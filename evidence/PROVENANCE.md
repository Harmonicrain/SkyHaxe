## G2a — SWF containers and the zlib bitmap family — PASS 2026-09-01

G2's first sub-gate. **348 assertions, 44 assets compared byte-for-byte**, zero console errors, in
a fresh browser tab.

### What "compared" means here

The reference in `evidence/g2_reader_contract.json` is a **second, independent implementation** —
Python with `zlib`/`lzma`/PIL — against Haxe with `haxe.zip.InflateImpl`. The contract is stated
explicitly so the two can only agree deliberately:

```
pixels = straight (un-premultiplied) RGBA8888, row-major, 4 bytes per pixel
hash   = sha256 of those bytes
```

Two independent decoders agreeing catches what actually goes wrong here — scanline padding,
premultiplied alpha, colormap sizing, the erroneous JPEG header, LZMA framing. **It is not the
same claim as parity with the Flash client**, which G2's own "done when" asks for. That comparison
is tracked as G2c through G2e in CHECKLIST.md rather than quietly folded into the G2a/G2b passes.

### Canary set

Eight files, each chosen for a reason rather than by convenience:

| File | Container | Proves |
|---|---|---|
| `15pillow.swf` | CWS | the corpus baseline: Lossless2 + BinaryData |
| `01_dragonlamp_skream.swf` | FWS | uncompressed container |
| `vip_sof5.swf` | FWS | the corpus's only `DefineBitsLossless` (tag 20) |
| `BW_HeadmasterChair.swf` | CWS | `DefineBitsJPEG3` |
| `elephants.swf` | **CWS-no-adler** | the checksumless case P1c found in live content |
| `ads_tvoh_crate1.swf` | ZWS | deferred to G2c |
| `hh_game_bb_room.swf` | ZWS | deferred; 311 PNG-in-JPEG2 characters |
| `hh_game_bb.swf` | ZWS | deferred; 14 MP3 exports |

Deferred files are **declared and asserted** — the test fails if the deferral count changes — so
coverage cannot quietly shrink.

### Fetched over HTTP, not from `C:\`

`scripts/serve-g2.py` serves the built page at `/` and mounts the read-only corpus at `/ngh/` on
the **same origin**. A second port would have failed on CORS as an artefact of the rig rather than
of the client. Requests are GET/HEAD only and every path is resolved and checked against the
corpus root, so `..` cannot escape.

Aggregate over the five parsed canaries: **cold 0.065s, warm 0.033s** (fetch plus full parse).

### The corpus finding this turned up

`evidence/g2_embedded_format_survey.py` scans every JPEG-family character in the measured corpus,
reading only files the G0/P1c CSVs already flag rather than re-walking 21,000 SWFs:

| Corpus | Result |
|---|---|
| Gordon (reachable) | `DefineBitsJPEG2 -> png` **1,468** · `JPEG3 -> jpeg` 734 · `JPEG3 -> png` 57 |
| `dcr/` | `JPEG3 -> jpeg` 1,036 · `JPEG2 -> jpeg` 3 · `JPEG3 -> png` 2 · `JPEG2 -> png` 2 |

**Not one reachable Gordon `DefineBitsJPEG2` is actually a JPEG**, and three `dcr/` files mix both
codecs inside a single SWF. SWF 8 permits PNG and GIF89a in those tags. The consequence for the
reader is concrete: dispatch on payload magic per character, and never apply the `JPEG3` alpha
block to a PNG payload — it carries its own alpha.

That trap is not hypothetical. The first version of the reference decoder forced every JPEG-tag
payload through `.convert("RGB")` and set alpha to 255, which would have silently dropped the
alpha channel on all 1,468 characters while still producing plausible-looking images. It was
caught by a PIL warning, not by the comparison.

PLAN.md's D1 and CHECKLIST's G2 both said "two decoder families"; both now say three, with the
correction recorded in place.

## G2b — browser PNG/JPEG payloads — PASS 2026-09-01

A fresh OpenFL/Chrome tab passed **499 assertions with 68 compared assets** and zero console
errors. The expanded nine-file canary set adds `godin.swf`, whose exported symbols mix JPEG and
PNG inside the same FWS file, proving that dispatch is per character rather than per tag or file.

PNG stays lossless and byte-identical to the independent Pillow reference after both sides use
BitmapData's visible-pixel convention: fully transparent pixels are transparent black. PNG files
may retain arbitrary invisible RGB below alpha 0; hashing that encoder residue was a contract bug,
not display parity.

JPEG is lossy, so exact RGB SHA-256 equality between Pillow and Chrome is invalid: their IDCT and
colour conversion may round differently. Across 18 JPEG characters, SWF/JPEG3 alpha was exact
(zero differing alpha samples), while Chrome versus Pillow RGB differed by at most **1** channel
value with an aggregate mean of **0.1931**. The regression bounds are max 2 and mean 0.5 per
character. G2e remains the authority for comparison with Flash itself.

Evidence: `evidence/g2b_verification.json`. Current contract hashes include the independent
compressed RGBA reference bytes used for bounded browser/Pillow comparison.

## G4b correction — theme-driven window rendering, 2026-09-02

G4b passed on 2026-09-02 with six visible defects, all spotted by the owner within minutes of
looking at the page: a white button caption, a button at its authored width, that button
off-centre once narrowed, a non-bold caption, a left-aligned frame title, and the whole page
CSS-scaled ~1.87x and interpolated.

**The gate did not fail because its evidence had no way to fail.** `g4b_verification.json` carried
a `matched` list and no `differences` list, and the comparison was a human side-by-side. The
figures it recorded were true; the omissions were invisible. It now carries
`differences_found_and_fixed`, each entry naming the defect, its cause, and the source that
settles it.

### The underlying mistake

Every defect traced to the same thing: the renderer approximated each control in code. The client
does not work that way. It ships `habbo_element_description_xml.bin` — 332 rows binding
`(type, style)` to a skin asset and an internal window layout — plus 44 `habbo_window_layout_*`
documents that declare each control's own child windows, tags, params, text styles and margins.
Those documents use the same schema as application layouts, so the existing parser reads them
unchanged.

Reading them deleted more code than it added: `BUTTON_TEXT_INSET`, `TITLE_BAR_TEXT_Y`,
`resolveButtonWidth`, the `button_shiny_bold` / `u_frame_title` defaults, the per-control caption
positioning, and the hardcoded `frame_3` content offset. In their place, `inherit_caption`,
`expand_to_accommodate_children`, the resize-align and relative-scale params, `_CONTENT` and style
inheritance are handled generically. The title bar's help and close buttons appeared without being
written.

Two rules had to cross the theme boundary before this worked, and both cost a wrong guess first:
`inherit_caption` propagates from internal children into ordinary ones (the `_TITLE` label lives in
`header_container`'s `<children>`), and so do the relative-scale params. Both were found by adding
`WindowController.describe()` — a structural tree dump — after guessing wrong twice. The dump is
retained: when a control renders wrongly, the first question is whether the theme resolved the
child it should have, and that is far quicker to read off a tree than to infer from a screenshot.

### Two files that should be generated, not hand-written

Recorded against M2's exception-manifest rule (`m2_recost.md`, requirement 5):

| Hand-written today | Existing AS3 counterpart |
|---|---|
| `src/com/sulake/core/window/utils/ParamCodeTable.hx` | `com/sulake/core/window/utils/ParamCodeTable.as` |
| `src/com/sulake/core/window/enums/WindowParam.hx` | `com/sulake/core/window/enum/WindowParam.as` |

Both are transcriptions of source that already exists and should be converter output at M2b/M2d,
not hand-maintained exceptions. `TruffleText`, `ElementDescription` and `InternalLayouts` have no
AS3 counterpart and are genuine exceptions.

This session is evidence **for** the M2 refresh architecture rather than against it: hand-written
approximation is what produced every defect here, and the correction still added two files that a
converter should have produced.
